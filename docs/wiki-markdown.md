# 위키 확장 마크다운 설계

## 확정 문법

### RP 이름과 후리가나

```markdown
명총희[+시라유키 히나]
{어둠 속의 명총희}[+시라유키 히나]
{명총희}[+[시라유키 히나](https://example.com/profile)]
{명총희}[+[치지직:b044e3a3b9259246bc92e863e7d3f3b8]{시라유키 히나}]
```

첫 형태는 `[+...]` 직전의 연속된 유니코드 문자·숫자·밑줄을 본문으로 사용한다. 괄호나 마침표가 이름 **바깥**에 있으면 `“명총희[+시라유키 히나]”`처럼 자연스럽게 멈춘다. 공백, 문장부호 또는 인라인 서식을 본문에 포함하려면 `{...}` 형태를 사용한다.

```markdown
{어둠 속의 명총희}[+시라유키 히나]
{**명총희** 2기}[+Shirayuki Hina]
{[명총희](https://example.com/profile)}[+시라유키 히나]
```

`명총희.[+시라유키 히나]`와 `**명총희**[+시라유키 히나]`는 직전 단어와 표식 사이에 문장부호 또는 인라인 토큰 경계가 있으므로 암시형으로 묶지 않는다. 각각 `명총희.[+시라유키 히나]`를 그대로 쓰거나 `{**명총희**}[+시라유키 히나]`처럼 명시한다.

출력은 의미를 보존하는 `<ruby>`/`<rt>` 구조다. 후리가나 안에서는 일반 텍스트와 기존 인라인 Markdown 링크 및 플랫폼 선언을 처리한다. 중첩 후리가나와 블록 문법은 처리하지 않는다. 플랫폼 이름 링크는 기존처럼 선언 이후, 문서 순서, 유일한 이름이라는 조건을 그대로 따른다. RP 전체를 링크로 감싸지 않으므로 중첩 링크가 생기지 않는다.

기본 배치는 CSS의 두 행 그리드와 가운데 정렬을 사용한다. 글꼴과 아이콘이 적용된 뒤 두 행의 실제 픽셀 너비를 한 번씩 측정해 짧은 행에만 자간을 배분한다. 한 글자에는 자간을 넣지 않고, 자간은 글자 크기의 45%로 제한한다. 화면보다 긴 RP는 문서 폭을 밀어내지 않도록 행 내부 줄바꿈을 허용한다.

### 같은 문서 제목 링크

```markdown
{무면라이더}[->공무직 오리엔테이션 (2026.09.12)]
```

표시명만 링크가 되고 대상은 현재 문서에서 목차 대상이 되는 실제 제목이다. 제목 단계와 링크의 앞뒤 위치는 무관하다. 대상 문자열은 제목의 번호 마커를 제외한 표시 텍스트와 비교하며, 인라인 강조·링크 태그는 텍스트만 남긴다. 현재 목차의 평문 추출 방식과 마찬가지로 후리가나 본문과 주석 텍스트는 모두 포함하고 아이콘 자체는 포함하지 않는다.

검색 문자열은 NFC 유니코드 정규화, 양끝 공백 제거, 연속 공백 하나로 정리만 수행한다. 대소문자와 문장부호는 보존해 서로 다른 제목을 과도하게 합치지 않는다. 연결에는 Kramdown이 이미 생성한 실제 제목 `id`를 사용한다.

- 같은 표시 제목이 여러 개면 문서의 첫 번째 제목으로 연결하고 `duplicate` 진단을 반환한다.
- 대상이 없으면 표시명을 평문으로 보존하고 `missing` 진단을 반환한다. `#` 링크는 만들지 않는다.
- 진단은 요소의 `data-wiki-heading-status`, `wiki-heading-diagnostics` 이벤트와 `wikiMarkdown.resolveHeadingLinks()` 반환값으로 노출한다. 현재 편집기 UI가 없으므로 별도 대형 UI는 추가하지 않는다.
- 링크는 실제 `<a href="#실제-id">`이므로 Enter 키, URL 해시, 새로고침, 뒤로 가기와 직접 URL 진입은 브라우저 기본 동작을 따른다. 기존 제목의 `scroll-margin-top`이 고정 헤더 여백을 제공하며, 별도 강제 스크롤이나 포커스 이동을 추가하지 않는다.

## 파싱 순서와 예외

파서는 원문을 왼쪽부터 읽고 기존 강조·코드 스팬·HTML 자동 링크·HTML 인라인·각주 표식 순서를 유지한다. 새 문법은 기존 Markdown 링크 파서 직전에 등록되며 `[+`와 `{: ...}`가 아닌 `{`만 처리한다. 코드 블록은 블록 파서가 먼저 분리하고, 백슬래시 이스케이프는 표식 시작 전에 문자를 소비한다. 기존 링크 안에서는 새 문법을 만들지 않는다. RP 내부 조각은 기존 인라인 파서로 처리하며, 재귀 강조·링크 내부에서도 중첩 RP 파싱을 비활성화한다. 제목 링크의 표시명은 평문으로 추출해 중첩 링크를 방지한다.

빈 본문·후리가나·이동 대상, 닫히지 않은 괄호, 연결 표식이 다른 중괄호는 원문을 잃지 않고 평문으로 둔다. 괄호는 기존 토큰 파서에 넘길 내부 조각을 찾기 위해 이스케이프와 중첩된 같은 종류의 괄호를 세어 닫으므로, 후리가나 안의 복잡한 Markdown 링크나 플랫폼 선언이 바깥 괄호를 조기에 닫지 않는다. 새 요소의 URL 처리는 기존 Markdown 링크 파서와 플랫폼 ID 검증을 그대로 거친다.

## 후속 개선 우선순위

| 우선순위 | 항목 | 효과 | 복잡도 | 제안 |
| --- | --- | --- | --- | --- |
| P1 | 깨진 내부 링크 진단 UI | 제목 변경·삭제의 영향을 작성 중 즉시 발견 | 중간 | 이번에 추가한 진단 이벤트를 편집 화면의 행·요약 경고에 연결한다. |
| P1 | 제목 자동완성 | 오타와 깨진 링크를 입력 단계에서 예방 | 중간 | `{표시}[->` 입력 시 현재 AST의 제목 표시명과 실제 ID를 후보로 제공한다. |
| P2 | 안정적인 제목 참조 | 제목 변경과 중복 제목에도 링크 유지 | 높음 | `{표시}[->#영구-id]`와 제목의 명시적 `{#id}`를 우선 지원하고, 표시명 참조는 호환 문법으로 유지한다. 중복 항목 지정도 ID로 해결한다. |
| P2 | 편집기 삽입 도구 | 중괄호·대괄호 실수 감소 | 중간 | 선택 영역을 본문/표시명으로 채우는 RP·제목 링크 명령을 추가한다. |
| P3 | 문법 도움말 | 신규 작성자의 학습 비용 감소 | 낮음~중간 | 이 문서의 복사 예제와 동일 렌더러를 쓰는 미리보기를 도움말에 노출한다. |

자동완성·삽입 UI와 영구 ID 참조는 현재 저장소에 범용 위키 편집기가 없어 핵심 렌더링과 분리했다. 진단 데이터 계약은 이번 구현에 포함해 후속 UI가 파서를 다시 바꾸지 않도록 했다.

## 검증 결과와 제한

- Ruby 파서 테스트: 기본·확장 RP, 한 글자, 링크·플랫폼 선언, 괄호가 포함된 코드/URL, 중첩 방지, 잘못 닫힌 입력 보존, 기존 속성·이미지·강조·각주 통과.
- Jekyll 3.10.0 실제 빌드 및 위키·작성·제목 통합 테스트, JavaScript 자동 링크·탐색·정규화 테스트 통과.
- Chrome 데스크톱·320px 다크 화면에서 실제 너비·작은 치지직 아이콘·긴 RP 내부 줄바꿈을 확인했다. 320px 화면에서 문서 scrollWidth는 319px, 긴 RP는 부모 263px 안에 표시되었다. 정상·중복·없는 제목의 상태와 링크 유무, Enter 활성화·새로고침·뒤로 가기도 확인했다.
- 제목 연결은 브라우저에서 실제 DOM ID를 조회하므로 JavaScript가 필요하다. JavaScript 없이 RP는 CSS 가운데 정렬로 표시되며 제목 링크는 표시명 평문으로 남는다. 기존 GitHub Markdown 미리보기는 사용자 정의 파서를 지원하지 않으므로 로컬 Jekyll 미리보기로 확인해야 한다.
- 자간 보정에는 실제 너비를 사용하고, 글자 수는 늘릴 간격의 수에만 사용한다. 큰 너비 차이는 0.45em 한도에서 가운데 정렬한다. 화면을 넘는 RP만 행 내부 줄바꿈한다.
- 현재 목차와 동일하게 제목 주석 텍스트도 검색에 포함한다. 플랫폼 선언이 제목에 직접 쓰이면 서버 목차의 원래 선언 텍스트를 기준으로 검색한다. 후속 작업에서 공통 표시 텍스트 모델로 통합할 수 있다.
- 이 저장소는 작성자가 관리하는 HTML을 허용하는 기존 Kramdown 정책을 유지한다. 새 HTML 정화기나 URL 허용 범위를 추가하지 않는다.
